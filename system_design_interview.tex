\subsection{Step 1 - Understand the Problem and Establish Design Scope}

Yelp supports many features and it is not feasible to design all of them in an interview seesion, so it's important to narrow down the scope by asking questions

The interactions between the candidate and interviewer could look like this:

\begin{itemize}
\item
Candidate: Can a user specify the search radius? If there are not enough businesses within the search raidus, does the system expand the search?
\item
Interviewer: That's a great question. Let's assume we only care about businesses within a specified radius. If time allows, we can then discuss how to expand the search if there are not enough binesses within the radius
\item
Candidate: Can a user change the search radius on the UI?
\item
Interviewer: Yes, we have the following options: 0.5km (0.31 mile), 1km (0.62 mile), 2km (1.24 mile), 5km (3.1 mile), and 20 km (12.42 mile)
\item
Candidate: How does business information get added, deleted, or updated? Do we need to reflect these operations in real-time?
\item
Interviewer: Business owners can add, delete or update a business. Assume we have a business agreement upgfront that newly added/updated businesses will be effective the next day.
\item
Candidate: A user might be moving while using the app/website, so the search results could be slightly different after a while. Do we need to refresh the page to keep the results up to date?
\item
Interviewer: Let's assume a user's moving speed is slow and we don't need to constantly refresh the page
\end{itemize}

\subsection{Functional requirements}

Based on this conversation, we focus on 3 key features:

\begin{itemize}
\item
Return all businesses based on a user's location (latitidue and longitude pair) and radius
\item
Business owners can add, delete, or update a business but this information doesn't need to be reflected in real time
\item
Customers can view detailed information about a business
\end{itemize}

\subsection{Non-functional requirements}

From the business requirements, we can infer a list of non-functional requirements. You should also check these with the interviewer.

\begin{itemize}

Low latency: Users should be able to see nearby businesses quickly
\item
Data privacy: Location info is sensitive data

\begin{itemize}
\item
When we design a location-based service (LBS), we should always take user privary into consideration
\item
We need to compy with data privacy laws like General Data Protection Regulation (GDPR) [4] and California Consumer Pirvacy Act (CCPA) [5], etc.
\item
High availability and scalability requirements: We should ensure our system can handle the spike in traffic during peak hours in densely populated areas
\end{itemize}

The high level design diagram is shown in Figure 1.2. The system comprises two parts: location-based service (LBS) and business-related service. Let's take a look at each component of the system.

\subsection{Location-based service (LBS)}

The LBS service is the core part of the system which finds nearby buisnesses for a given radius and location.

The LBS has the following characteristics:

\begin{itemize}
\item
It is a read-heavy service with no write requests
\item
QPS is high, espcially during peak hours in dense areas
\item
This service is stateless so it's easy to scale horizontally
\end{itemize}

\subsection{Business service}

Business service mainly deals with two types of requests:

\begin{itemize}
\item
Business owners create, update, or delete businesses. Those requests are mainly write operations, and the QPS is not high
\item
Customers view detailed information about a business. QPS is high during peak hours
\end{itemize}

\subsection{Database cluster}

\begin{itemize}
\item
The database cluster can use the primary-secondary setup
In this setup, the primary database handles all the write operations, and multiple replicas are used for read operations
\item
Data is saved to the primary database first and then replicated to replicas
\item
Due to the replication delay, there might be some discrepancy between data read by the the LBS and the data written to the primary database
\item
This inconsistency is usually not an issue because business information doesn't need to be updated in real-time
\end{itemize}

\subsection{Scalability of bsuiness service and LBS}

Both the bisness service and LBS are stateless services, so it's easy to autmatically add more servers to accommodate peak traffic (e.g. mealtime) and remove servers during off-peak hours (e.g. sleep time)

If the system operates on the cloud, we can set up different regions and availability zones to further improve availability [9]. We discuss this more in deep dive.

\subsection{Option 4: Quadtree}

Another popular solution is quadtree

\begin{itemize}
\item
A quadtree [18] is a data structure that is commonly used to partition a two-dimensional space by recursively subdividing it into four quadarants (grids) until the contents of the grids meet certain criteria
\item
For example, the criterion can be to keep sudividing until the number of businesses in the grid is not more than 100
\item
This number is arbitrary as the actual number can be determined by business needs
\item
Witha  quadtree, we build an in-memory tree structure to answer queries
\item
Note that quadtree is an in-memory data structure and it is not a database solution
\item
It runs on each  LBS server, and the data structure is built at server start-up time
\item
The following figure visualizes the conceptual process of subdividing the world into a quadtree
iiLet's assume the world contains 200m (million) businesses
\end{itemize}

\begin{figure}[H]
  \begin{center}

\end{figure}

\begin{itemize}
\item
Figure 1.14 explains the quadtree building process in more detail.
\item
The root node represents the whole world map.
\item
The root node is recusively broken down into 4 quadrants until no nodes are left with more than 100 businesses
\end{itemize}

\begin{figure}[H]

The pseudo code for building quadtree is shown below:

\begin{lstlisting}
public void buildQuadtree(TreeNode node) {
  if (countNumberOfBusinessesInCurrentGrid(node) > 100) {
    node.subdivide();
  }
  for (TreeNode child: node.getChildren()) {
    buildQuadTree(child);
  }
}
\end{lstlisting}

\subsection{How much memory does it need to store the whole quadtree?}

To answer this question, we need to know what kind of data is stored.

Table 1.6: Leaf Node \\
\begin{tabular}{|p{6cm}|p{6cm}|}
\hline
Name & Size \\
\hline
Top left coordinates and bottom-right coordinates to identify the grid & 32 bytes (8 bytes $\times$ 4) \\
\hline

\hline
Total & 832 bytes\\
\hline
\end{tabular}

Table 1.7: Internal Node \\
\begin{tabular}{|p{6cm}|p{6cm}|}
\hline
Name & Size \\
\hline
Top left coordinates and bottom-right coordinates to identify the grid & 32 bytes (8 bytes $\times$ 4) \\
\hline
Pointers to 4 children & 32 bytes (8 bytes $\times$ 4)\\
\hline
Total & 64 bytes\\
\hline
\end{tabular}

Even though the tree-building process depends on the number of businesses within a g rid, this number does not need to be store in the quad tree node because it can be inferred from records in the database.

Now that we know the data structure for each node, let's take a look at the memory usage.

\begin{itemize}
\item
Each grid can store a maximal of 100 businesses
\item
Number of leaf noes =~ $\frac{200 \text{ million}}{100} =\sim 2 \text{ million }$
\item
Number of internal notes = $2 \text{ million} \times \frac{1}{3} =\sim 0.67 \text{ million }$. If you do not know why
the number of internal nodes is one-third of the leaf nodes, please read the reference material [19]
\item
Total memory requirement = $2 \text{ million} \times 832 \text{ bytes} + 0.67 \text{ million} \times 64 \text{ bytes} =\sim 1.71 \text{ GB}$
\end{itemize}

In a real interview, we shouldn't need such detailed calculations.

\begin{itemize}
\item
The key takeway here is that the quadtree index doesn't take too much memory and can easily fit in one server.
\item
Does it mean we should use only one server to store the quadtree index?
\item
The answer is no
\item
Depending on the read volume, a single quadtree server might not have neough CPU or network bandwidth to server.
\end{itemize}

\subsection{How long does it take to build the whole quadtree?}

Each leaf node contains approximately 100 business IDs.

\begin{itemize}
\item
The time complexity to build the tree is $\frac{n}{100} \text{log} \frac{n}{100}$, where $n$ is the total number of businesses
\item
It might take a few minutes to build the whole quadtree with 200 million businesses
\end{itemize}

\subsection{How to get nearby businesses with quadtree?}

\begin{itemize}
\item
Rebuild the quaddtree in memory
\item
After the quadtree is built, start search from the root and traverse the tree, until we find the leaf node where the seach origin is
\item
If that leaf node has 100 businesses, return the node
\item
Otherwise, add businesses from its neighbors until enough businesses are returned
\end{itemize}

\subsection{Operational considerations for quadtree}

As mentioned above, it may take a few minutes to build a quadtree with 300 million businesses at the server start0up time.

\begin{itemize}
\item
It is important to consider the operational implications of such a long server start-up time
\item
While the quadtree is being built, the server cannot serve traffic
\item
Therefore, we should roll out a new release of the server incrementally to a small subset of servers at a time
\item
This avoids taking a large swath of the server cluster offline and causes service brownout
\item
Blue/green deployment [20] can also be used, but an entire cluster of new servers fetching 200 million businesses at the same time from the
database service can put a lot of strain on the system
\item
This can be done, but it may complicate the design and you should mention that in the interview
\item
Another operational consideration is how to update the quadtree as businesses are added and removed over time
\item
The easiest approach would be to incrementally reuilb d the quadtree, a small subset of servers at a time, across the entire cluster,
\item
But this would mena some servers would return stale data for a short period of time
\item
However, this is generally an acceptable compromise based on the requirements
\item
This can be further mitigated by setting up a business agreement that newly added / updates businesses will only be effective the next day
\item
This means we can update the cache using a nightly job
\item
One potential problem with this approach is that tons of keys will be invalidated at the same time, causing heavly load on cache servers
\item
It's also possible to update the quadtree o9n the fly as businesses are dadded and removed
\item
This certainly complicates the design, especially if the quadtree data structure could be accesssed by multiple threads
\item
This will require some locking mechanism which could dramatically complicate the quadtree implementation
\end{itemize}

\subsection{Geohash vs quadtree}

Before we conclude this section, let's do a quick comparison between geohash and quadtree

\subsubsection{Geohash}

\begin{itemize}
\item
Easy to use and implement. No need to build a tree
\item
Supports returning businesses within a specified radius
\item
When the precision (level) of geohash is fixed, the size of the grid is fixed as well. It cannot dynamically adjust the grid size, based on population density
\item
More complex logic is needed to suppport this
\item
Updating the index is easy. For example, to remove a business from the index we jsut ened to remove it from the corresponding row with the same \lstinline|geohash| and \lstinline|business_id|. See Figure 1.18 for a concrete example.
\end{itemize}

\subsection{Quadtree}

\begin{itemize}
\item
Slightly harder to implement because it eneds to build a tree
\item

\begin{itemize}
\item
Supports fetching k-nearest businesses and don't care if businesses are within a specified radius
\item
For example, when you are traveling and your car is low on gas, you just want to find the nearest \lstinline|k| gas stations
\item
These gas stations may not be near you, but the app needs to return the nearest \lstinline|k| results
\item
For this type of query, a quadtree is a good fit because its subdividing process is based on the number \lstinline|k| and it can automatically adjust the query range until it returns \lstinline|k| results
\item
It can dynamically adjust the grid size based on population desnity (see the Denver example in Figure 1.15)
\item
\begin{itemize}
\item
Updating the index is more complicated than geohash
\item
A quadtree is a tree stucture
\item
If a business is removed, we need to traverse from the root to the leaf node, to remove the business
\item
For example, if we want to remove the business with \lstinline|ID = 2|, we have to travel from the root all the way down to the leaf node, as shown in Figure 1.19
\item
Updating the index takes \lstinline|O(log n)|, but the implementaiton is complicated if the sdata structure is accessed by a multi-threaded program, as locking is required
\item
Also, reblaancing the tree can be complicated
\item
Rebalacning is necessary if, for exmaple, a leaf node has no room for a new addition
\item
A possible fix is to over-allocate the ranges
\end{itemize}
\end{itemize}

\subsection{Scale the geospatial index}

One common mistake about scaling the geosptail index is to quickly jump to a sharding scheme without considering the actual data size of the table.

\begin{itemize}
\item
In our case, the full dataset for the geospatial index table is not large (quadtree index only takes 1.71G memory and storage requirement for geohash index is similar)
\item
The whole geospatial index can easily fit in the working set of a modern database server.
\item
HOwever, depending on the read volume, a single database server mgiht not have enough CPU or network badnwidth to hanlde all read requests
\item
If that is the case, it is necessary to spread the read load among multiple database servers
\item
There are two general approaches for spreading the load of a relational database server
\item
We can add read replicas, or shared the database
\item
Many engineers like to talk about sharding during interviews
\item
However, it might not be a good fit fo rthe geohash table as sharding is complicated
\item
For instance, the sharding logic has to be added to the application layer
\item
Sometimes, sharding is only option
\item
In this case,t hough, everything can fit in the working set of a database server, so there is no strong technical reason to shard the data among multiple servers
\item
A better approach, in this case, is to have a series of read replicas to help with the read load
\item
This method is much simpler to develop and maintain
\item
For this reason, scaling the geospatial index table through replicas is recommended
\end{itemize}

\subsection{Caching}

Before introducing a cache layer we ahve to ask ourselves, do we really need a cache layer?

It is not immediately obvious that caching is a solid win:

\begin{itemize}
\item

\begin{itemize}
\item
The workload is read-heavy, and the dataset is relatively small
\item
The data could fit in the working set of any modern database server
\item
Therefore, the queries are not I/O bound and they should run almost as fast as an in-memory cache
\end{itemize}

\item
If read performance is a bottleneck, we can add database read replicas to improve the read throughput
\end{itemize}

Be mindful when discussing caching with the interviewer as it will require careful bench marking and cost analysis. If you find out
caching does fit the business requirements then you can proceed with discussions about caching strategy.

\subsection{Cache key}

The most straightforward cache key choic is the location coordinates (latitude and longitude) of the user.

However, this choice has a few issues:

\begin{itemize}
\item
\begin{itemize}
\item
Location coordinates returned from mobile phones are not accurate as they are just the best estimation [32]
\item
Even if you don't move, the results might be slightly different each time you fetch coordinates on your phone
\end{itemize}

\item
\begin{itemize}
\item
A user can move from one location to another, causing location coordinates to change slightly
\item
For most applications, this change is not meaningful
\end{itemize}
\end{itemize}

Therefore, location coordinates are not a good cache key. Ideally, small changes in location should still map to the same cache key.

The geohash/quadtree solution mentioned earlier handles this problem well because all businesses within a grid map to the same geohash.

\subsection{Why don't we use a database to store location data?}

The ``Nearby friends'' feature only cares about the \textbf{current} location of a user.

Therefore, we only need to store one location per user.

\begin{itemize}

\item
If the Redis instance goes down, we could replace it with an empty new instance and let the cache be filled as new location updates stream in
\item
The active users could miss location updates from friends for an update cycle or two while the new cache warms

It is an acceptable tradeoff
\item
In the deep dive section, we will dicuss ways to lessen the impact on users when the cache gets replaced

\subsection{Step 3: Design Deep Dive}

The high-level design we created in the previous section works in most cases, but it will likely break at our scale.

In this section, we work together to uncover the bottlenecks as we increase the scale, and along the way work on solutions to
eliminate those bottlenecks.

\subsection{How well does each component scale?}

\subsubsection{API servers}

The methods to scale the RESTful API tiers are well understood. These are statless servers, and there are many ways to auto-scale the
clusters based on CPU usage, load, or I/O. We will not go into detail here.

\subsubsection{WebSocket servers}

For the WebSocket cluster, it is not difficult to auto-scale based on usage.

\begin{itemize}
\item
However, the WebSocket servers are stateful, so care must be taken when removing existing nodes
\item
Before a node can be removed, all existing connections should be allowed to drain
\item
To achieve that, we can mark a node as ``draining'' at the load balancer so that no new WebSocket connections will be routed to the draining server
\item
Once all the existing connections are closeed (or after a reasonably long wait), the server is then removed
\end{itemize}

Release a new version of the application software on a WebSocket server requires the same level of care.

It is worth nothing that effective auto-scaling of stateful servers is the job of a good load balancer.

Most cloud loud balancers handle this job very well.

\subsubsection{Client initialization}

The mobile client on start up establishes a persisten WebSocket connection with one of the WebSocket server instances.
\begin{itemize}
\item
Each connection is long running.
\item
Most modern languages are capable of maintaining many long-running connections with a reasonably small memory footprint
\item
When a WebSocket connection is initialized the client sends the initial location of the user, and the server performs the following tasks in the WebSocket conenction handler.
\end{itemize}

\begin{enumerate}
\item
It updates the users's location in the location cache
\item
It saves the location in a variable of the connection handler for subsequent calculations
\item
It loads all the user's friends from the user database
\item

\begin{itemize}
\item
It makes a batched request to the location cache to fetch the locations for all the friends
\item
Note that because we set a TTL on each entry in the location cache to match out inactivity timeout period, if a friend is inactive then their location will not be in the location cache
\end{itemize}
\item
\begin{itemize}
\item
For each location returned by the cache, the server computes the distance between the user and the friend at that location
\item
If the distance is within the search radius, the friend's profile, location, and last updated timestamp are truend over the WebSocket
connection to the client
\end{itemize}
\item

\begin{itemize}
\item
For each friend, the server subscribes to the frien's channel in the Redis Pub/Sub server
\item
We will explain our use of Redis Pub/Sub shortly
\item
Since creating a new channel is cheap, the user subscribes to all active and inactive friends
\item
The inactive friends will take up a small amount of memory on the Redis Pub/Sub server, but they will not consume any CPU or I/O (since they do not publish updates) until they come online
\end{itemize}
\item
It sends the user's current location ot the user's channel in the Redis Pub/Sub server
\end{enumerate}

\subsection{User database}

The user database holds two distinct sets of data: user profiles (user ID, username, profile URL, etc.) and friendships.

\begin{itemize}
\item
These datasets at our design scale will likely not fit in a single relational database instance: The good news is that the data is horizintally scalable by sharding based on user ID
\item
Relational database sharding is a very common technique
\item
As a side note, at the scale we are designing for, the user and friendhsip datasets will likely be managed by a dedicated team and be
available via an internal API.
\item
In this scenario the WebSocket servers will use the internal API instead of querying the database directly to fetch user and friendship-related data
\item
Whether accessing via API or direct database queries, it does not make much difference in terms of functionality or performance
\end{itemize}

\subsection{Location cache}

We chooose Redis to cache the most recent locations of all active users.

\begin{itemize}
\item
As mentioned earlier, we also set a TTL on each key.
\item
The TTL is renewed upon every location update
\item
This puts a cap on the maximum amount of memory used
\item
With 10 million active users at peak, and with each location taking no more than 100 bytes, a single modern Redis server with many GBs
of memory should be able to easily hold the location information for all users.
\item
However, with 10 million active users roughly updateing every 30 seconds, the Redis server will have to handle 334k updates per second
\item
That is likely a little too high, even for a modern high-end server
\item
Lucily, this cache data is easy to shared
\item
The location data for each user is independent, and we can evenly spread the laod among several Redis servers by sharding the location data based on user ID
\item
To improve availability, we could replicate the location data on each shared to a standby node
\item
If the primary node goes down, the standby could be quickly promoted to minimize downtime
\end{itemize}

\subsection{Redis Pub/Sub server}

The Pub/Sub server is used as a routing layer to direct messages (location updates) from one user to all the online friends.

\begin{itemize}
\item
As mentioned earlier, we choose Redis Pub/Sub ecause it is very lightweight to create new channels.
\item
A new channel is created when someone subscribes to it
\item
If a message is published to a channel that has no subscribes, the message is dropped, placing very little load on the server
\item
When a channel is created, Redis uses a small amount of memory to maintain a hash table and a linked list [3] to track the subscribers
\item
If there is no update on a channel when a user is offline, no CPU cycles are used after a channel is created
\end{itemize}

We take advantage of this oin our design in the following ways:

\begin{enumerate}
\item

\begin{itemize}
\item
We assign a unique channel to every user who uses the ``nearby friends'' feature
\item
A user would, upon app initialization, subscribe to each friend's channel, whether the friend is online or not
\item
This simplifies the design since the backend does not need to handle subscribing to a frien's channel when the friend becomes active, or handling, unsubscribing when the friend becomes inactive
\end{itemize}

\item

\begin{itemize}
\item
The tradoff is that the design would use more mmory
\item
As we will see later, memory use is unlikely to be the bottleneck
\item
Trading higher memory use for a simpler architecture is worth it in this case
\end{itemize}
\end{enumerate}

\subsection{How many Redis Pub/Sub servers do we need?}

Let's do some math on memory and CPU usage.

\subsubsection{Memory usage}

Assuming a channel is allocated for each user who uses the nearby firneds feature, we need 100 million channels ($1 \text{ billion} \times 10\%$)

\begin{itemize}
\item
Assuming that on average a user has 100 active friends using this feature (this includes friends who are bnearyby, or not), and it takes about 20 bytes of pointers in the internal hash table and linked list to track across each subscriber, it will need about 200GB ($100 \text{ million} \times 20 \text{ bytes} \times 100 \text{ friends} / 10^{9} = 200 \text{ GB}$) to hold all the channels
\end{itemize}

\subsection{CPU usage}

As previously calculated, the Pub/Sub server pushes about 14 million updates per second to subscribers.

\begin{itemize}
\item
Even though it is not easy to esimate with any accuracy how many messages a modern Redis server could push a second without actual benchmarking, it is safe to assume that a single Redis server will not be able to handle that load
\item
Let's pick a conservative number and assume that a modern server with a gigabit netowrk could handle about 100000 subscriber pushes per second
\item
Given how small our location update messages are, this number is likely to be conservative
\item
Using this conservative estimate, we will need to distribute the load among 14 million / 100000 = 140 Redis servers.
\item
Again, this number is liekly too conservative, and the actual number of servers could be much lower
\end{itemize}

From the math, we conclude that:

\begin{itemize}
\item
The bottleneck of Redis Pub/Sub server is the CPU usage, not the memory usage
\item
To support our scale, we need a distributed Redis Pub/Sub cluster
\end{itemize}

\subsection{Scaling considerations for redis Pub/Sub servers}

How should we scale the Redis Pub/Sub server cluster?

\begin{itemize}
\item
Should we scale it up and down daily, based on traffic patterns?
\item
This  is a very common practice for stateless servers because it is low risk and saves costs
\item
To answer these questions, let's examine some of the properties of the Redis Pub/Sub server cluster
\end{itemize}

\begin{enumerate}
\item

\begin{itemize}
\item
The messages sent on a Pub/Sub channel are not persisted in memory or on disk
\item
They are not sent to all subscribes of the channel and removed immediately after
\item
If there are no subscribers, the messages are just dropped
\item
In this sense, the data going through the Pub/Sub channel is stateless
\end{itemize}

\item

\begin{itemize}
\item
However, there are indeed states stored in the Pub/Sub servers for the channels
\item
Specifically, the subscriber list for each channel is a key piece fo the states tracked by the Pub/Sub servers
\item
If a channel is moved, which ould happen when the channel's Pub/Sub server is replaced, or if a new server is added or an old server removed on the hash ring, then every subscriber to the moved channel must known about it, so they could unsubscribe from the channel on the old server and resubscribe to the replacement channel on the new server
\item
In this sense, a Pub/Sub server is stateful, and coordination with all subscribers to the server mus be orchestrated to mimimize service interruptions
\end{itemize}
\end{enumerate}

For these reasons, we should treat the Redis Pub/Sub cluster more like a stateful cluster, similar to how we would handle a storage cluster.

\begin{itemize}
\item
With stateful clusters, scaling up or down has some operational overhead and risks, so it should be done with careful planning
\item
The cluster is normally over-provisioned to make sure it can handle daily peak traffic with some comfortable headroom to avoid unnecessary resizing of the cluster
\end{itemize}

When we inevitably have to scale, be mindful of these potential issues:

\begin{itemize}
\item

\begin{itemize}
\item
When we resize a cluster, many channels wil be moved to different servers on the hash ring
\item
Whe the service discovery component notifies all the WebSocket servers of the hash ring update, there will be a ton of resubscription requests
\end{itemize}

\item

\begin{itemize}
\item
During these mass resubscription events, some location updates might be missed by the clients
\item
Although occasional misses are acceptable for our design, we should minimized the occurences
\end{itemize}
\item
Because of the potential interruptions, resizing should be done when usage is at it slowest in the day
\end{itemize}

How is resizing actually done? It is quit simple. Follow these steps:
\begin{itemize}
\item
Determine the new ring size, and if scaling up, provision enough new servers
\item
Update the keys of the hash ring with the new content
\item
Monitor your dashboard. There should be some spike in CPU usage in the WebSocket cluster.
\end{itemize}

Using the hash ring from Figure 2.9 above, if we were to add 2 new nodes, say, \lstinline|p_5|, and \lstinline|p_6|, the hash
ring would be updated like this:

This includes the language component (Erlang or Elixir [8]) and the runtime environment and libraries (the Erlang virtual machine called BEAM [9] and the Erlang runtime libraries called OTP [10])
\item
The power of Erlang lies in its lightweight processes
\item
An Erlang process is an entity running on the BEAM VM
\item
It is several orders of magnitude cheaper to create than a Linux process
\item
A minimal Erlang process takes about 400 bytes, and we can have millions of these processes on a single modern server
\item
If there is no work to do in an Erlang process, it just siets there without using any CPU cycles at all
\item
In other words, it is extremely cheap to model each of the 10 million active users in our design as an individual Erlang process
\item
Erlang is also very easy to distribute among many Erlang servers
\item
The operational overhead is very low, and there are great tools to support debugging live production issues, safely
\item
The deployment tools are also very strong
\item
How would we use Erlang in our design?
\item
We would implement the WebSocket service in Erlang, and also replace the entire dcluster of Reis Pub/Sub with a distributed Erlang application
\item
In this application, each user is modeled as an Erlang process
\item
the user process would receive updates from the WebSocket server when a user's location is updated by the client
\item
The user process also subscribes to updates from the Erlang processes of the user's friends
\item
Subscription is native in Erlang/OTP and it's easy to build
\item
This forms a mesh of connections that would efficiently route location updates from one user to many friends
\end{itemize}

Most routing algorithms are variations of Dijkstra's or A* pathfinding algorithms.

\begin{itemize}
\item

\item

    \caption{}
  \end{center}

The pathfinding performance for most of these algorithsm is extreneley sensitive to the size of the graph.

\begin{itemize}
\item
Representing the entire world of road networks as a single graph would consume too much memory and is liekly too large for any of these algorithms to run efficiently
\item
The graph needs to be broken up into manageable units for these algorithsm to work at our design scale
\item
One way to break up road networks around the world is very similar to the tiling concept we discussed for map rendering
\item
By employing a similar subdivision technique as geohasing, we divide the world into small grids
\item
For each grid, we convert the raods whithin the grid into a small graph data structure that consists of the nodes (intersections) and

\item
We call these grids routing  tiles
\item
Each routing title holds rreferences to all the other tiles it connects to
\item
This is how the routing algorithms can stitch together a bigger road graph as it traverses these interconnected routing tiles
\item
By breaking up raod networks into routing tiles that can ve loaded on demand, the routing algorithms can significantly reduce memory consumption and improve pathfinding performance by only consuming a small subset of the routing tiles at a time, and only loading additional tiles as needed

\subsection{Map rendering}

As we discussed in the back-of-the-envelope estimation, the entire collection of map tiles at various zoom levels is about a hundred
petabytes in size.

It is not practical to hold the entire dataset on the client

The map tiles must be fetch on-demand from the server based on the client's location and the zoom level of the client viewport.

Whwne should the client fetch new map tiles from the server? Here are some scenarios:

\begin{itemize}
\item
The user is zooming and panning the map viewpoint on the client to explore these surroundings
\item
During navigation, the user moves out of the current amp tile into a nearby tile.
\end{itemize}

We are dealing with a lot of data. Let's see hwo we could serve these map tiles from the server efficiently.

\subsection{Option 1}

The server builds the map tiles on the fly, based on the client location and zoom level of the client viewport.

Considering that there is an infinite number of location and zoom level combinations, generating map tiles dynamically has a few severe disadvantages:

\begin{itemize}
\item
It puts a huge load on the server cluster to generate every map tile dynamically
\item
Since the map tiles are dynamically generated, it is hard to take advantage of caching
\end{itemize}

\subsection{Option 2}

Another option is to server a pre-generated set of map tiles at each zoom level.

\begin{itemize}
\item
The map tiles are static, with each tile convering a fixed rectangular grid using a subdivision schema like geohashing
\item
Each tile is therefore represented by its geohash
\item
In other words, there is a unique geohash associated with each grid
\item
When a client needs a map tile, it first determines the map tile collection to use based on its zoom level
\item
It then computes the map tile URL by converting its location to the geohash at the appropriate zoom level
\item
These static, pre-generated images are served by a CDN as shown in Figure 3.10.
\end{itemize}

\subsection{Message queues vs event streaming platforms}

Strictly speaking, Apache Kafka and Pulsar are not message queues as they are event streaming platforms.

However, there is a convergence of features that starts to blur the distinction between message queues (RocketMQ, ActiveMQ, RabbitMQ, ZeroMQ, etc.) and event streaming platforms (Kafka, Pulsar).

\begin{itemize}
\item
For example, RabbitMQ, which is a typical message queue, added an optional streams to allow repeated message consumption and long message retention, and its implementation uses an appened-only log, much like an event streaming platform would
\item
Apache Pulsar is primarily a Kafa competitor but it is also flexible and performant enough to be used as a typical distributed message queue
\end{itemize}

In this chapter, we will design a distributed message queue with \textbf{additional features, such as long data retention, repeated consumption of messages, etc.,} that are typically only available on event streaming platforms.

These additional features make the design more complicated.

Throughout the chapter, we will highlight places where the design could be simplified if the focus of your interview centers around the more traditional distributed message queues.

\subsection{Step 1: Understand the Problem and Establish Design Scope}

In a nutshell, the basic functionality of a message queue is striaghtforward: producers send messages toa queue, and consumers consume messages from it.

Beyond this basic functionality, there are other considerations including performance, message delivery semantics, data detention, etc.

THe following set of questions will help clarify requirements and narrow down the scope.

\begin{enumerate}
\item
\textbf{Candidate}: What's the format and average size of messages? Is it text only? Is multimedia allowed?

\textbf{Interviewer}: Text messages only. Messages are generally measured in the range of kilobytes (KBs)
\item
\textbf{Candidate}: Can messages be repreatedly consumed?

\textbf{Interviewer}:

\begin{itemize}
\item
Yes, messages can be repeatedly consumed by different consumers.
\item
Note that is an added feature.
\item
A traditional distributed message queue does not retain a message once it has been successfully delivered to a consumer
\item
Therefore, a message cannot be repeatedly consumed in a traditional message queue
\end{itemize}

\item

\textbf{Candidate}: Are messages consumed in the same order they were produced?

\textbf{Interviewer}:

\begin{itemize}
\item
Yes, messages should be consumed in the same order they were produced
\item
Note that this is an added feature
\item
A traditional distributed message queue does not usually guarantee delivery orders
\end{itemize}
\item

\textbf{Candidate}: Does data need to be persisted and what is the data retention?

\subsection{Step 3: Design Deep Dive}

To achieve high throughput while satisfying the high data retention requirement, we made three important design choices, which we explain in detail now.

\begin{itemize}
\item

\item

\item
\begin{itemize}
\item
We dicussed the message data structure to allow a message to be passed from the producer to the queue and finally to the consumer, with no modifications

\item

\begin{itemize}

Small I/O is an enemy of high throughput
\item
SO, wherever possible, our deisng encourages batching

The message queue persists messages in even larger bathces

\subsection{Data storage}

Now let's explore the options to persist messages in more detail, In order to find the best choice, let's consider the trafffic pattern of a message queue.

\begin{itemize}
\item
Write-heavy, read-heavy
\item
\begin{itemize}
\item
No update or delete operations
\item
As a side note, a traditional message queue does not persist messages unless the queue falls behind, in which case there will be ``delete'' operations when the queue cathces up
\item
What we are talking about here is the persistence of a data streaming platform
\end{itemize}
\item
Predominantly sequential read/write access.
\end{itemize}

Option 1: Database

The first option is to use a database.

\begin{itemize}
\item
Relational database: create a topic table and write messages to the table as rows
\item
NoSQL database: create a collection as a topic and write messages as documents
\end{itemize}

Databases can handle the storage requirement, but they are not ideal because it is hard to design a database that supports both write-heavy and read-heavy access patterns at a large scale.

The database solution does not fit our specific data usage patterns very well.

This means a database is not the best choice and could become a bottleneck of the system.


Option 2: Write-ahead log (WAL)

The second option is write-ahead log (WAL).

\begin{itemize}
\item
WAL is just a plain file where new entries are appended to an append-only log
iiWAL  is used in many systems, such as the redo log in MySQL [4] and the WAL in ZooKeeper
\item
We recommend persisting messages as WAL log files on disk
\item
WAL has a pure sequential read/write access pattern
\item
The disk performance of sequential access is very good [5]
\item
Also, rotational disks have large capacity ant they are pretty affordable
\item
As shown in Figure 4.9, a new message is appended to the tail of a partition, witha monotonically increasing offset
\item
THe easiest option is to use the line number of the log file as the offset
\item
However, a file cannot grow infinitely, so it is a good idea to divide it into segments
\item
With segments, new messages are appended only to the active segment file
\item
When the active segment reahces a certain size, a new active segment is created to receive new messages, and the currently active segment becomes inactive, like the rest of the non-active segments
\item
Non-active segments only serve read requests
\item
Old non-active-segment files can bvbe truncated if they exceeed the retention or capacity limit
\end{itemize}

\subsubsection{Push vs Pull}

AN importatn question to answer is wehetare brokers should push data to consumers, or if consumers should pull data from the brokers.

\subsubsection{Push model}

Pros:

\begin{itemize}
\item
Low latency. The broker can push messages ot the consumer immediately upon receiving them
\end{itemize}

Cons:

\begin{itemize}
\item
If the rate of consumption falls below the rate of production, consumers could be overwhelmed
\item
It is difficult with consumers with diverse processing power because the brokers control the rate at which data is transferred
\end{itemize}

\subsubsection{Pull model}

Pros:

\begin{itemize}
\item
Consumers control the consumption rate. We can have on set of consumers process messages in real-time and another set of consumers process messages in batch mode
\item
If the rate of consumption falls below the rate of production, we can scale out the consumers, or simply catch up when it can
\item
\begin{itemize}
\item
The pull model is more suitable for batch processing
\item
eeIN the push model, the broker has no knowledge of whether consumers will be able to prcess messages immediately
\item
If the broker sends one message at a atime to the consumer and the consumer is backed up, new messages wil end up waiting in the buffer
\item
A pull model pulls all available messages after the consumer's current position in the log (or up to the configurable max size)
\item
It is suitable for aggressive batching of data.
\end{itemize}
\end{itemize}

Cons:

\begin{itemize}
\item
When there is no message in the broker, a consumer might still keep pulling data, wasting resources, to overcome this issue, many message queues support long polling mode, which allows pulls to wait a specified amount of time for new messages[6].
\end{itemize}

Based on these considerations, most message queues choose the pull model.

\subsection{In-sync replicas}

We mentioned that messages are persisted in multiple partitions to avoid single node failure, and each partition has multiple replicas.

\begin{itemize}
\item
Messages are only written to the leader, and followers ysnchronize data from the leader
\item
One problem we need to solve is keeping them in sync
\item
In-sync replicas (ISR) refer to replicas that are ``in-sync'' with the leader
\item
The definition of ``in-sync'' depends on the topic configuration
\item
For example, if the value of replica.lag.max.messages is 4, it means that as long as the follower is behind the leader by no more than 3 messages, it will not be removed from ISR [10]
\item
The leader is an ISR by default
\end{itemize}

Let's use an example as shown in Figure 4.24 to sshows how ISR works

\begin{itemize}
\item

\begin{itemize}
\item
The committed offset in the leader replica is 13
\item
Two new messages are written to the leader, but not committed yet
\item
Committed offset means that all messages before and at this offset are already synchronized to all the replicas in ISR
\end{itemize}
\item
Replica-2 and replica-3 have fully caught up with the leader, so they are in ISR and can fetch new messages
\item
Replica-4 did not fully catch up with the leader within the configured lag time, so it is not in ISR. When it catches up again, it can be added to ISR
\end{itemize}

\begin{figure}[H]
  \begin{center}
    \includegraphics[width=0.8\linewidth]{figure_4_24}
    \caption{}
  \end{center}
\end{figure}

Why do we need ISR?

\begin{itemize}
\item
The reason is that ISR reflects the trade-off between performance and durability
\item
If producers don't want to lsoe any messages, the safest way to do that is to ensure all replicas are already in sync before sneding an acknoewledgment
\item
But a slow replica will cause the whole partition to become slow or unavailable
\item
Now that we've discussed ISR, let's take a look at acknowledgment settings
\item
Producers can choose to receive acknowledgments until the $k$ number of ISRs has received the messager, where $k$ is configurable
\end{itemize}

Now let's look at the consumer side. The easiest setup is to let consuemrs connect to a leader replica to consume messages.

You might be wondering if the leader replica would be overwhelmed by this design and why messages are not read from ISRs. The reasons are:

\begin{itemize}
\item
Design and operational simplicity
\item

\item
The number of connections to the leader replicas is usually not large as long as a topic is not super hot
\item
If a topic is hot, we can scale by expanding the number of partitions and consumers
\end{itemize}

In some scenarios, reading from the leader replica might not be the best option

\begin{itemize}
\item
For example, if a consumer is located in a different data center from the leader replica, the read performance suffers
\item
In this case, it is wrothwhile to enable consumers to read from the closest ISRs
\item
Interested readers can checkout the reference material about this [11]
\item
ISR is very important

How does it determine if a replica is ISR or not?
\item
Usually, the leader for every partition tracks the ISR list by computing the lag of every replca from itself.
\item
If you are interested in detailed algoriths, you can find the implementations in reference materials [12] [13]
\end{itemize}

Let's use an example in Figure 4.28 to explain how failure recovery works.

\begin{enumerate}
\item
Assume there are 4 brokers and the partition (replica) distribution plan is shown below:

\begin{itemize}
\item
Partition-1 of topic A: replicas in Broker-1 (leader), 2, and 3
\item
Partition-2 of topic A: replicas in Broker-2 (leader), 3, and 4
\item
Partition-1 of topic B: replicas in Broker-3 (leader), 4, and 1
\end{itemize}
\item
Broker-3 crashes, which means all the partitions on the node are lost.

The partition distribution plan is changed to

\begin{itemize}
\item
Partition-1 of topic A: replicas in Broker-1 (leader) and 2
\item
Partition-2 of topic A: replicas in Broker-2 (leader) and 4
\item
Partition-1 of topic B: replicas in Broker-4 and 1
\end{itemize}

\item
The broker controller detects Broker-3 is down and generates a new partition distribution plan for the remaining broker nodes:

\begin{itemize}
\item
Partition-1 of topic A: replicas in Broker-1 (leader), 2, and 4 (new)
\item
Partition-2 of topic A: replicas in Broker-2 (leader), 4 and 1 (new)
\item
Partition-1 of topic B: replicas in Broker-4 (leader), 1, and 2 (new)
\end{itemize}
\item
The new replicas work as followers and catch up with the leader
\end{enumerate}

To make the broker fault-tolerant, here are additional considerations:

\begin{itemize}
\item

\begin{itemize}
\item
The minimum number of ISRs specifies how many replicas the producer must receive before a message is considered to be succesfully committed
\item
The higher the number, the safer
\item
But on the other hand, we need to balance latency and safety
\end{itemize}

\item

\begin{itemize}
\item
If all replicas of a partition are in the same broker node, then we cannot tolerate the failure of this node
\item
It is also a waste of resources to replicate data in the same node
\item
Therefore, replicas should not be in the same node
\end{itemize}

\item

\begin{itemize}
\item
If all the replicas of a partition crash, the data for that partition is lost forvever
\item
When choosing the number of replicas and replica locations, there's a trade-off between data safety, resource cost, and latency
\item
It is safer to distribute replicas across data centers, but this will incur much more latency and cost, to synchronize data between replicas
\item
As a workaround, data mirroring can help to copy data across data centers, but this is out of scope
\item
The reference material [14] covers this topic
\end{itemize}
\end{itemize}

Now let's get back to discussing the scalability of brokers.

However, there is a better approach. The broker controller can temporarily allow more replcas in the system than the number of replicas in the config file.

WHen the newly added broker catches up, we can remove the ones that are no longer needed.

\subsection{Data delivery semantics}

As the name suggests, at-most once means a message will be delivered not more than once. Messages may be lost but are not redelivered.

This is how at-most once delivery works at the high level.

\begin{itemize}
\item
The producer sends a message a asynchronously to a topic without waiting for an acknowledgment (ACK=0). If message delivery fails, there is no retry.
\item
\begin{itemize}
\item

Consumer fetches the message and commits the offset before the data is processed.
\item
 If the consumer crashes just after offset commit, the message will not be reconsumed.
\item
On the other hand, if a consumer processes the message but fails to commit the offset to the broker, the message will be re-consumed when the consumer restarts, resulting in duplicates
\end{itemize}

\item
A message might be delivered more than once to the brokers and consumers
\end{itemize}

  \begin{center}

    \caption{}
  \end{center}
\end{figure}

Use cases: With at-least once, messages won't be lost but the same message might be delivered multiple times.

\begin{itemize}
\item
While not ideal from a user perspective, at-least once delivery semantics are usually good enough for use cases where data duplication is not a big issue or deduplication is possible on the consumer side
\item
For example, with a unique key in each message, a message can be rejected when writing duplicate data to the database.
\end{itemize}

\subsubsection{Advanced features}

In this section, we talk briefly about some advanced features, such as message filtering, delayed messages, and scheduled messages.

\subsubsection{Message filtering}

A topic is a logical abstraction that contains messages of the same type.

\begin{itemize}
\item
However, some consumer groups may only want to consume messages of certain subtypes
\item
For examples, that the ordering system sends all the activites about the order to a topic, but the payment system only cares about messages related to checkout and refund.
\item
One option is to build a dedicated topic for the payment system and another topic for the ordering system
\end{itemize}

This method is simple, but it might raise some concerns.

\begin{itemize}
\item
What if other systems ask for different subtypes of messages? Do we need to build dedicated topics for every single consumer request?
\item
It is a waste of resources to save the same messages on different topics
\item
The producer needs to change every time a new consumer requirement comes, as the producer and consumer are now tightly coupled
\end{itemize}

Therefore, we need to resolve this requirement using a different approach.

Luckily, message filtering comes to the rescue.

A naive solution for message filtering is that consumer fetches the full set of messages and filters out unnecessary messages during processing time.

\begin{itemize}
\item
This approach is flexible but introduces unnecessary traffic that will affect system performance
\item
A better solution is to filter messages on the broker side so that consumers wil only get messages they care about
\item
Implementing this requires some careful consideration
\item
If data filtering requires data decryption or deserialization, it will degrade the performance of the brokers
\item
Additionally, if messages contain sensitive data, they should not be readable in the message queue
\item
Therefore, the filtering logic in the broker should not extract the message payload
\item
It is better to put data used for filtering into the metadata of a emssage, which can be efficiently read by the broker
\item
For example, we can attach a tag to each message
\item
With a message tag, a broker can filter messages in that dimension
\item
If more tags are attached the messages can be filtered in multiple dimensions
\item
Therefore, a list of tags can support most of the filtering requirements
\item
To support more complex logic such as mathematical formulae, the broker will need a grammar parser or a script executor, which might be too heavyweight for the message queue
\item
With tags attached to each message, a consumer can subscribe to messages based on the specfied tag, as shown in Figure 4.35
\item
Interested readers can refer to the reference material [15]
\end{itemize}

\subsection{Data storage system}

The data storage system is the heart of the design.

\begin{itemize}
\item
It's not recommended to build your own storage system or use a general-purpose storage system (for example, MySQL [10]) for this job.
\item
A general-purpose database, in theory, could support time-series data, but it would require expert-level tuning to make it work at our scale
\item
Specifically, a relational database is not optimized for operations you would commonly perform against time-series data
\item
For example, computing the moving average in a rolling time window requires complicated SQL that is difficult to read (there is an example of this in the deep dive section)
\item
Besides, to support tagging/labeling data, we need to add an index for each tag
\item
Moreover, a general-purpose relational database does not perform well under constant heavy write load
\item
At our scale, we would need to expend significant effort in tuning the database, and even then, it might not perform well
\item
How about NoSQL?
\item
In theory, a few NoSQL databases on the market could handle time-series data effectively
\item
For example, Cassandra and BigTable [11] can both be used for time series data
\item
However, this would require deep knowledge of the internal workings of each NoSQL to deivse a scalable schema for effectively storing and querying time-series data
\item
With industrial-scale time-series databases readily available, using a general-purpose NoSQL database is not appealing
\end{itemize}

There are many storage systems available that are optimized for time-series data.

\begin{itemize}
\item
The optimization lets us use far fewer servers to handle the same volume of data
\item
Many of these databases also have custom query interfaces specially designed for the analysis of time-series data that are much easier to use than SQL
\item
Some even provide features to manage data retention and data aggregation
\item
Here are a few exaqmples of time-series databases
\end{itemize}

OpenTSDB is a distributed time-series databse, but since it is based on Hadoop and HBase, running a Hadoop/HBase cluster adds complexity

\begin{itemize}
\item
Twitter uses MetricsDB [12] and Amazon offers Timestream as a time-series database [13]
\item
According to DB-engines [14], the two most popular time-series databases are InfluxDB [15] and Prometheus, which are designed to store large volumes of time-series data and quckly perform real-time analysis on that data
\item
Both of them primarily rely on an in-memory cache and on-disk storage
\item
And they both handle durability and performance quite well
\item
As shown in Figure 5.5, an InfluxDB with 8 cores and 32GB RAM can handle over 250,000 writes per second
\end{itemize}

\begin{figure}[H]

In a push model, a collection agent is commonly installed on every server being monitored.

\begin{itemize}
\item
A collection agent is a piece of long-running software that colelcts metrics from the services running on the server and pushes those metrics periodically to the metrics collector
\item
The collection agent may also aggregate metrics (especifally a simple counter) locally, before sending them to metric collectors
\item
Aggregation is an effective way to reduce the volume of data sent to the metrics collector
\item
If the push traffic is high and the metrics collector rejects the push with an error, the agent could keep a small buffer of data locally (possibly by storign them locally on disk), and resend them later
\item
However, if the servers are in auto-scaling roup where they are rotated our frequently, then holding data locally (even temporarily) might result in data loss when the metrics collector falls behind
\item
To prevent the metrics collector from falling behind in a push model, the metrics collector should be in an auto-scaling cluster with a load balancer in front of it (Figure 5.13)
\item
The cluster should scale up and down based on the CPU load of the metric collector servers
\end{itemize}

\subsection{Where aggregations can happen}

Metrics can be aggregated in different places; in the collection agent (on the client-side), the ingestion pipeline (before writing to storage), and the query side (after writing to storage)

Let's take a closer look at each of them.

\begin{enumerate}
\item
\textbf{Collection agent}:

The collection agent installed on the client-side only supports simple aggregation logic. For example, aggregate a counter every minute before it is sent to the metrics collector

\item

\textbf{Ingestion Pipeline}:

\begin{itemize}
\item
To aggregate data before writing to the storage, we usually need stream processing engines such as FLink
\item
The write volume will be significantly reduced since only the calculated result is written to the database
\item
However, handling late-arriving events could be a challenge and another downside is that we lose data precision and some flexibility because we no longer store the raw data
\end{itemize}
\item
\textbf{Query side}:

Raw data can be aggregated over a given time period at query time

There is no data loss with this approach, but the query speed might be slower because the query result is computed at query time and is run against the whole dataset.

\end{enumerate}

The query service comprises a cluster of query servers, which access the time-series databases and handle requrest from the visualizatoin or altering system

\begin{itemize}
\item
Having a dedicated set of query servers decouples time-series databases from the clients (visualziation and alerting systems)
\item
And this gives us the flexibility to change the time-series database or the visualization and altering systems, whenever needed
\end{itemize}

\subsubsection{Time-series database query language}

Most popular metrics monitoring systems like Prometheus and InfluxDB don't use SQL and have their own query languages.

ONe major reason for this is that it is hard to build SQL queries to query time-series data.

For example, as metnioned here [27], computing an exponential moving average might look like this in SQL:

\begin{lstlisting}
select id,
       temp,
       avg(temp) over (partition by group_nr order by time_read)
       as rolling_avg
from (
    select id,
           temp,
           time_read,
           interval_group,
           id - row_number() over (partition by interval_group
                                    order by time_read) as group_nr
    from (
        select id,
               time_read,
               "epoch"::timestamp + "900 seconds"::interval *
                   (extract(epoch from time_read)::int4 / 900) as interval_group,
               temp
        from readings
    ) t1
) t2
order by time_read;

\subsection{Space optimization}

As explained in high-level requirements, the amount of metric data to store is enourmous. Here are a few strategies for tackling this.

\subsection{Data encoding and compression}

Data encoding and compression can significantly reduce the size of data. Those features are usually built into a good time-series database. Here is a simple example.

\begin{figure}[H]
  \begin{center}
    \includegraphics[width=0.8\linewidth]{figure_5_18}
    \caption{}
  \end{center}
\end{figure}

As you can see in the image above, 1610087371 and 1610087381 differ by only 10 seconds, which takes only 4 bits to represent, instead of the full timestamp of 32 bits

So, rather than storing absolute values, the delta of the values can be stored along with one base value like: 1610087371, 10, 10, 9, 11.

\subsection{Downsampling}

Downsampling is the process of converting high-resolution data to low-resolution to reduce overall disk usage.

Since our data retention is 1 year, we can downsample old data.

For example, we can let engineers and data scientists define rules for different metrics.

Here is an example:

\begin{itemize}
\item
Retention: 7 days, no sampling
\item
Retention: 30 days, downsample to 1 minute resolution
\item
Retention: 1 year, downsample to 1 hour resolution
\end{itemize}
